The one rule that catches everyone

Do not leave print() statements or function calls in your file. This is by far the most common reason a student's work is marked wrong when every answer in it is correct.

CodeGrade runs your file and then calls your objects itself to check them. To grade Q1 it runs Q1() and reads what comes back. If your file already printed something, or already called Q1(), that output lands in the middle of what CodeGrade is trying to read, and the comparison fails.

✓ Submit this

Q1 = 'Welcome to EU!'
Q2 = 1+1

✗ Not this

Q1 = 'Welcome to EU!'
print(Q1)

Q2 = 1+1
print(Q2)

The same rule for functions - define them, do not call them:

✓ Submit this

def Q3(x):
    return x * 2

✗ Not this

def Q3(x):
    return x * 2

Q3(5)
So how do you test your work? Test it freely while you are working - that is the point of a notebook. Then, before you submit, either comment the test lines out with # or delete them. Keeping them in one cell at the bottom makes them easy to find. Or run the checker above, which will tell you if you missed one.

Something went wrong

What is happening?

The three reasons you lose credit

  1. Instructions were not followed - file name, variable names, libraries, or how the data was loaded.
  2. Your file crashes. See the warning below - this one is worth understanding properly.
  3. Your values are not correct.
If your file crashes, you earn zero - even where your values are right. CodeGrade cannot reach question 8 if question 3 stopped the file. This also means you can lose marks you already had: if you change a working file and introduce an error, correct answers below the error stop counting.

Annoying, yes. But code that crashes in real life has consequences too, and "most of it ran" is not a defence anybody accepts.

Where to look in CodeGrade

The Errors tab tells you what went wrong. A common one is a name that does not exist - if you called your answer Q100 when the assignment asked for Q1, CodeGrade reports that Q1 was never defined. Fix the name and it passes.

Function assignments

Define, don't assign

When the instructions say create a function named Q3, they mean a function. An assignment is not one:

✓ A function

def Q3():
    return 42

✗ Not a function

Q3 = 42

Indentation

The body of a function is indented. Anything after it, at the same level as def, is outside the function:

✓ Correct

def Q4(x):
    total = x + 1
    return total

✗ Wrong — line 3 is over-indented

def Q4(x):
    total = x + 1
        return total

An IndentationError naming a line number is telling you exactly where to look. The error translator explains the ones this course raises.

Arguments: when to take one

Some questions want a function that takes an argument and some do not, and getting it the wrong way round makes the answer fail. You can look this up rather than guessing: the Input tab in CodeGrade shows the exact command it uses to run your function. If it shows Q5() your function takes nothing; if it shows Q5(3) it takes an argument.

Notice what that tab is showing you: CodeGrade calls the function itself. Which is exactly why your own test call has to come out before you submit.

“check” questions

Some questions are named Q1check, Q4check and so on. These do not test your value - they test that you built the right kind of thing. A common one is checking you made a NumPy array rather than a plain Python list. Losing points on Q4check means Q4 exists but is the wrong type, so re-read what the question asked you to create.

Tips

  • One cell or many, it does not matter - as long as everything is present and nothing errors.
  • There is often more than one right way. Different approaches to slicing, for instance, all pass if the output is right.
  • Delete leftover cells. Not fatal, but a stray cell is usually the remains of something that should have gone.
  • Watch capitalisation. 'Hello World' and 'hello world' are different answers.
  • Watch strings against lists. 'a' is not ['a'].
  • Create random objects once. Creating one twice overwrites the first with new values. If your numbers do not match the expected output, restart the kernel and run everything from the top so the random sequence is the same one CodeGrade will get.

The practice assignment

Your first submission is deliberately easy - two questions, and the answers are given. The point is to see what submitting feels like before it counts.

  • Create a file called practice.ipynb.
  • Load no libraries. Later assignments may require them; read each assignment's instructions.
  • Create Q1, a string containing Welcome to EU!
  • Create Q2, equal to 1 + 1.
  • Do not print anything.

The whole file should be:

Q1 = 'Welcome to EU!'
Q2 = 1+1

Then run it through the checker at the top of this page, and submit.
